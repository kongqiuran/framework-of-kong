# 骨架：量化交易项目骨架

> 适用于：个人或小团队做量化交易（A 股 / 港股 / 美股 / 期货）的**工程组织方式**。
>
> 这个骨架解决的不是"怎么赚钱"，而是**"怎么保证自己不被自己骗"**。
> 量化最大的风险不是亏钱，而是**回测很漂亮、实盘完全不一样，且你找不到原因**。

---

## 核心原则（三条，缺一个都会翻车）

1. **先冻结规格，再写代码**。未写清楚"输入/输出/验收标准"之前不动手，否则会陷入"改一版跑一版"的无底洞。
2. **数据口径先于策略**。数据错 1%，策略结论可能完全反过来。所有"能赚钱的回测"都要先回答"数据可信吗"。
3. **门禁靠代码，不靠自觉**。人（尤其是自信的人）在结果好看时会自动放过风险；把放行条件写成程序判据，比自己发誓有用。

> 与《V3-规格驱动开发流程》配合使用：本骨架提供量化特有的**数据/策略门禁**，V3 提供通用的**八阶段流水线**。

## 一、目录结构骨架

```
<项目根>/
├── docs/
│   ├── specs/          # 规格：项目宪章、规格说明书、澄清记录、任务清单
│   ├── adr/            # 架构决策记录（每个重要取舍一份，不留在聊天里）
│   ├── 验证账本.md      # 所有门禁状态的证据总账（本项目最关键的文件）
│   └── 开源调研报告.md  # 选型的证据基础（星数/许可证/实测结论）
├── research/
│   └── probes/         # 可行性验证脚本（证据资产，不是产品代码）
├── data/
│   ├── raw/            # 原始数据缓存（附 *_meta.json）
│   └── curated/        # 加工后的特征数据
├── src/<pkg>/
│   ├── datasource/     # 【唯一允许联网的模块】多源适配 + 缓存 + 对账
│   ├── features/       # 派生特征（严格时点约束）
│   ├── strategy/       # 策略（只输出信号，不含执行）
│   ├── engine/         # 撮合/回测引擎
│   ├── risk/           # 风控门禁（硬代码一票否决）
│   └── evaluation/     # 信号校验评估（胜率/盈亏比/回撤/漂移）
├── tests/              # 单元测试 + 防前视专项测试
├── scripts/            # 入口脚本（数据管道、回测、报告）
├── requirements.txt    # 版本锁定（量化依赖极易漂移）
└── pytest.ini          # src 布局：pythonpath = src
```

**两条硬规矩**：
- **只有 `datasource` 能联网**，其他模块只读本地。这样"联网行为"可审计，回测可复现。
- **`engine` 不依赖第三方回测库**（可自研极简撮合 + 用成熟库做对账）。开源回测库普遍带许可证限制（有的禁止商用、有的是 GPL/AGPL），自研主线可避免被绑定。

## 二、阶段门禁骨架

| 阶段 | 目标 | 出口状态 | 不通过的后果 |
|---|---|---|---|
| M0 规格冻结 | 写清范围与非目标 | `SPEC-DONE` | 不得写业务代码 |
| M1 数据管道 | 多源取数 + 缓存 + 对账 | `DATA-PASS` | 不得做任何策略研究 |
| M2 回测闭环 | 信号→回测→评估打通 | `SIM-PASS` | 不得谈参数优化 |
| M3 样本外 | 样本外验证 | `OOS-PASS` | **不得接触真实资金** |
| M4 研究线 | 研究性模块（如拥挤度） | 记录即可 | 不得污染主线代码 |
| M5 模拟盘 | 3~6 个月连续运行 | 偏差可解释 | 不得上实盘 |
| M6 小资金实盘 | 固定上限 + 停机条件 | 台账完整 | 触发回撤即停机 |

**关键约束**：M3 是生死线。**样本外不达标就停在这里**，不要抱着"再调调参数就好"的心态往下走——那正是过拟合的开始。

## 三、状态标记体系（跨阶段通用）

| 标记 | 含义 | 允许的表述 |
|---|---|---|
| `SPEC-DONE` | 规格已冻结确认 | "设计完成" |
| `DATA-PASS` | 数据质检 + 对账通过 | "数据可信" |
| `SIM-PASS` | 回测引擎与独立实现互相对账通过 | "回测可信" |
| `OOS-PASS` | 样本外达标 | "策略可能有正超额" |
| `PAPER-PASS` | 模拟盘阶段性达标 | "可考虑小资金" |
| `LIVE-PASS` | 实盘证据完整 | "实盘验证过" |
| `*—PENDING` | 未验证 | **必须如实标注，不得含糊** |

**禁止表述**："这套系统能赚钱"（未过 OOS-PASS 前）、"回测年化 X%"（没有样本外与成本情景时）。

## 四、证据账本制度（本骨架最有价值的部分）

`docs/验证账本.md` 必须回答三个问题，且**每个结论后面跟一条可复现证据**：

1. **当前做到哪了？** → 门禁状态总表（每行带证据链接/Git 哈希）
2. **凭什么说通过了？** → 命令 + 输出 + 数据文件 + 测试结果
3. **有什么已知局限？** → 局限清单（含"这条局限会影响什么"）

同时，**开发过程中发现的问题必须留痕**：被测试抓到的 bug、被实测推翻的假设、被迫修正的决策，都写进账本。
理由：这些"踩坑记录"是未来最值钱的部分——别人（和未来的你）不会重复踩，也会因此相信你的结论是认真得出的。

---

## 五、反直觉但必须坚持的几条

1. **"跑通了"不等于"用对了"**。管道跑通只是最低标准，还要有对账与异常检出。
2. **策略简单不等于策略有效**。最简单均线策略在样本外跑输买入持有是常态（本项目实测：样本外 +18.5% vs 基准 +51.8%）。
3. **成本敏感性小 ≠ 策略好**。低频策略的成本敏感性天然很小，这只说明"成本不是问题"，**不说明信号有价值**。
4. **数据源的"时通时断"必须当常态处理**。免费数据源会因域名、代理、反爬而随时失效。
5. **公开即失效**。研究结论可以公开，实盘参数与阈值不应公开。

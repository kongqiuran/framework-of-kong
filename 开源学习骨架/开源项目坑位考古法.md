# 开源项目坑位考古法

> 配套 [[GitHub开源学习法]] 使用。前者讲**怎么用开源资源学知识**，本文讲**怎么从开源项目里把"坑"挖出来**。
>
> 一句话：**读最终代码只能学到"它现在怎么做"，读补丁史才知道"哪些做法被证明是错的"。**
> 而人（和 AI）反复踩的坑**几乎全在边界上**，不在主流程上。

---

## 一、问题：为什么"读了大佬代码"还是会踩坑

| 以为学到的东西 | 实际学到的东西 | 缺的那一半 |
|---|---|---|
| 架构、主流程、API 用法 | 结论的集合（可以抄） | **边界的集合**（抄不到） |
| "它现在怎么做" | 一个"看起来完整"的解 | **哪些做法被证明是错的** |

**关键判断**：成熟项目的代码是**在一次又一次的事故中打补丁**补出来的。
框架思想很容易学会，真正的落实靠细节；而细节不在最终代码里，在**补丁史**里。

> **类比：芯片的 errata sheet**
> 厂商会公开"这颗片子有哪些已知坑、怎么绕"。datasheet 只给标称值，**errata 才是真相**；
> 而 errata 是厂商用真实事故换来的，买芯片就附送。
> 软件界的 errata = `CHANGELOG` + 带 issue 号的回归测试 + 已关闭的 bug issue。
> **选了自研（不用框架）= 同时放弃两份白送的东西：架构约束 + errata。两项都要单独记账。**

## 二、两条路径

| 路径 | 适用条件 | 做法 | 成本 |
|---|---|---|---|
| **① 读历史** | 对方有 CHANGELOG / issue / 提交规范 | 读 fix 类提交、带 issue 号的回归测试、Revert 记录 | 低 |
| **② 扫边界** | 对方**发现问题直接重构、不留记录** | 全区间 / 全参数差分比对，主动把边界逼出来 | 高 |

### ⚠️ 特殊情况：大佬不写补丁史，发现问题直接重构

重构擦掉了"过程"，但留下了"形状"。三条残留线索：

1. **测试最抗重构** —— 实现会被重写，测试极少被删。**测试用例是唯一以"错误"形式编码的知识**，
   成熟项目的 `tests/` 就是它的坑位地图。
2. **"看起来不必要"的代码** —— 魔数、特判分支、`# workaround`、多余的抽象层，
   先假设它们**各自对应一个真实事故**。**抄代码时被当作冗余删掉的，往往正是补丁本身。**
3. **git 层面** —— `git log --follow -p <file>`（单文件全史）、`git log -S"常量"`（pickaxe，挖被删掉的写法）、
   PR 讨论（重构通常附"为什么不这么做"）、旧版本 `pip download X==旧版` 直接 diff。

若以上全无 → 只能走路径 ②：**不读它的历史，用差分主动逼出它的边界。**

## 三、考古命令速查

```bash
# 只拿提交历史，不下载文件内容（体积极小；实测 rqalpha 全史仅 2.7MB）
git clone --filter=blob:none --no-checkout https://github.com/owner/repo.git

# 修复密度 = 该项目的坑密度与维护活性
git log --oneline --grep="fix" -i | wc -l

# 按领域找高频坑区（把关键词换成你的领域：dividend / commission / tax / NaN / align …）
git log --format="%ad | %s" --date=short --grep="关键词" -i

# 改了又撤回 = 反直觉决策（价值最高的信号）
git log --oneline --grep="revert" -i

# 被改最频繁的文件 = 反复打补丁的区域
git log --name-only --pretty=format: | sort | uniq -c | sort -rn | head -30

# 单文件全史 / 搜索某个常量或函数的引入与删除
git log --follow -p <path>
git log -S"某个常量名" --oneline

# 取单个文件（网络不稳时最可靠，带重试）
for i in 1 2 3 4 5; do git show "HEAD:<path>" && break; sleep 2; done
```

**读什么**：

| 优先级 | 对象 | 挖到什么 |
|---|---|---|
| 1 | `tests/` 目录（尤其带 issue 号的回归测试） | 真实事故 + 它的边界条件 |
| 2 | Revert / 反复修改同一处 | **"看起来对的改动实际是错的"** |
| 3 | CHANGELOG / release notes | 反复修的区域 = 高频坑区 |
| 4 | 已关闭的 bug issue（"与预期不符"类） | 最容易被人写成"想当然"的规格 |
| 5 | 端到端金标准快照（`outs/*.txt` 之类） | 对方认为"哪些输出必须一字不变" |

## 四、产出物：坑位地图（不是读书笔记）

每条坑位必须写成**四元组**，否则只是感想：

```
① 坑是什么（一句话，含正确做法）
② 证据（文件 / 提交哈希 / 测试断言 —— 可核查，不许"我印象里"）
③ 对我们意味着什么（当前项目是否受影响、影响路径）
④ 动作（改规格 / 加测试 / 登记待办 / 仅记录）
```

**坑位地图的定位 = 失败模式矩阵的外部输入。**
只靠自己想失败模式，受限于自己的经验；接上大佬的补丁史，才是"我想到的 + 几百人年踩出来的"。

### 分级落库建议

| 级别 | 判据 | 处理 |
|---|---|---|
| A | 与**当前阶段**直接冲突 | 立刻改规格 + 补测试 |
| B | 当前不受影响，**扩范围时必然撞上** | 登记进前置清单，不现在做 |
| C | 影响某个尚未实现的模块 | 写进该模块的实现注意事项 |
| D | 运行期/运维类 | 补监控或故障演练场景 |

## 五、反模式（这些做法都试过，都没用）

| 反模式 | 为什么无效 |
|---|---|
| 只读 README / 官方文档 | 文档写"应该怎么做"，不写"哪里会炸" |
| 只读最终代码 | 看到"正确答案"，看不到"错过的答案" |
| 把测试全绿当作理解正确 | 测试只验证"代码 = 我的理解"；理解错了照样全绿 |
| 抄代码时删掉"看不懂的部分" | 那些部分往往正是补丁 |
| 元问题（"架构对不对"）靠"去查资料" | 事实性存疑靠"去查"，**架构性存疑靠"横向审查"这个主动动作** |
| 一次性调研完就归档 | 坑位地图必须**跟着项目阶段增量更新**（新增依赖前先考古） |
| **对照表只写「做法 → 启示」两列** | 启示列是提取产物，两列结构把“压缩损失了什么”藏起来，事后无从审计 |
| 把“读到了”当成“提取到了” | 读到 ≠ 提取到；提取必然有损，必须有**可检查的字段**（去向列）来承载损失 |

## 六、实战案例（可核查）

**背景**：某量化项目连续两次出现"开源项目早已解决、我们仍然踩"的问题。

| 案例 | 事实 | 教训 |
|---|---|---|
| **第二次** | rqalpha 早已处理"创业板 ETF 自 2020-08-24 起 ±20%"与"十进制取整"；我们的规格写死 ±10%。若不做全区间比对，错误会一路绿灯 | 规格里的常量若给不出**事实来源**，就是定时炸弹 |
| **第三次** | NautilusTrader 明确写"回测与实盘**共用同一套引擎组件**"，这句原文**就抄在自己的调研报告里**，但提取启示时只取了后半截，架构约束那半截被无声丢弃 | **提问框架决定视野**：调研问题是"回测正确性"，架构信息就不产生启示 |
| **考古产出** | 挖 rqalpha（3761 提交 / 830 fix）：发现"最低佣金必须按订单累计（不能按成交收）"、"印花税税率 2023-08-28 当天从 0.1% 变 0.05%"、"下单前资金预估 ≠ 成交后实际扣费" 等 10 条坑位 | 这些**全部是自研容易漏、且测试难以自证**的细节 |
| **考古产出** | 挖 vectorbt：2026-07 才修"滚动标准差数值稳定性"（朴素平方和公式在**大偏移小方差**时灾难性抵消，改用 Welford + 条件数检测 + 重算） | **合成/常规测试数据测不出**——必须显式构造对抗用例（如 offset=1e14） |
| **考古产出** | 挖 akshare（877 提交 / 313 fix = 36%）：**接口失效是常态不是异常**；我们依赖最重的 ETF 接口恰是近期连修三次的区域 | 多源降级 / 缓存 / 对账 / 故障演练是必需品，不是加分项 |

## 七、写调研报告：引用即契约（防止“大佬已经说了、你却忽略了”）

> **比补丁史更基本的一层**：坑位考古解决“没读到”，本节解决“**读到了、提取时丢了**”。
> 真实事故：NautilusTrader「回测与实盘**共用同一套引擎组件**」这句**原文就抄在自己的调研报告里**，
> 提取启示时被无声丢弃；事后回扫发现六行引用里**四行有信息丢失**，且丢失**不随机**——
> 集中在「与当前任务无关」的信息上。

### 7.1 两条铁律

1. **每条引用拆成「信息单元」**（一句话常含 2~3 条独立信息），逐个标去向：
   ✅ 采纳（落到哪个文件/条目）｜❌ 拒绝（写理由）｜⏸ 暂缓（写触发条件）。
   **没有去向标签的信息单元 = 漏项**，不允许“消失”。
2. **对照表必须有「原文要点」列**（保留未压缩的近原文）。
   禁止只写「关键做法 → 对我们启示」两列——两列结构会把压缩损失藏起来，事后无从追溯。
   > **实测依据**（三份调研报告、同一作者、同一时期、同一类对照关系，**唯一变量是表结构**）：
   > 无原文列的两份 —— 一份有实质丢失、一份 **4/6 行**有丢失；
   > **有原文列的一份仅 2 处轻微缺失**。所以这条不是审美偏好，而是**丢失率的决定因素**。

### 7.2 三问检查（每条引用）

| # | 问题 | 答不出的后果 |
|---|---|---|
| 1 | 这句话包含几个独立信息单元？ | 说明没真正读懂，只是抄了一遍 |
| 2 | 每个单元的去向？（采纳/拒绝/暂缓 + 落点） | 会产生孤儿信息 |
| 3 | **“如果这条是对的，它会改变什么？”** | **答不出 → 这条引用不该留在文档里**（删掉，也比放着自欺好） |

### 7.3 检查时点与 AI 特例

- **冻结前回扫**：规格/方案冻结前，把所有引用重过一遍找孤儿信息。
  与「横向审查」并列：横向审查防**架构漏项**，引用回扫防**信息漏项**。
- **AI 特例（必须自我披露）**：AI 写调研文档时天然按“当前任务需要”组织信息，
  所以**看起来完整、结构漂亮**，但压缩损失极隐蔽。必须显式声明“本次提取的框架是什么”，
  并标注“该框架之外可能被丢弃的东西”。
- **发现丢失后**：保留原表不改历史，另立「回扫补正」节，逐条拆解信息单元。

### 7.4 为什么这比“写得更仔细”有用

信息丢失**不是态度问题，是流程缺陷**：提取必然是有损压缩，
只要“压缩损失了什么”没有被写成可检查的字段，丢失就会重复发生——无论人多仔细、AI 多强。
把“去向”变成**表格里的一列**，它才是可审计的。

## 八、差分优先：把大佬当裁判（对付「未知的未知」）

> 比补丁史、比引用回扫**更根本**的一层：**第一次做出来的东西必然有缺陷，再仔细也会漏**。

### 8.1 缺陷四分法与唯一的死角

| 类 | 例子 | 防御 | 能防住吗 |
|---|---|---|---|
| 已知的已知 | 规格写清的 | 单元测试 | ✅ |
| 已知的未知 | 有风险没想清 | 失败模式矩阵 | ✅ |
| 未知的已知 | 别人知道、我们不知道 | 补丁史 + 引用回扫 | ✅ |
| **未知的未知** | 没人知道，或没人觉得那是问题 | **无** | ❌ **只能相遇** |

**推论：漏掉的东西不是被“思考”发现的，是被“相遇”发现的。**
“想得更全”是幻觉，“查得更勤”才是工程。

可控杠杆只有一个——**增大接触面积**：

- 数据：全区间扫描 ＞ 抽样
- **实现：一个独立实现 ＞ 只用自己**（面积从“你想到的”变成“整个输入空间”）
- 输入：对抗用例 ＞ 正常输入

### 8.2 为什么必须拿大佬当裁判

**大佬的实现 = 已经替你踩过一遍的“第一次”，你不用付那个代价。**
这就是“站在巨人肩膀上”最值钱的地方——不是学他的结论，是**用他当裁判**。

| 场景 | 动作 |
|---|---|
| 大佬有实现 | **先跑通他的输出，再写自己的**；第一版不追求“对”，追求“**差异清单**” |
| 大佬有测试 | 把他的测试用例转成自己的（**测试是“错误的形式化”**） |
| 大佬有金标准快照 | 抄机制（全量输出存档比对，改动即红） |
| 大佬都没有 | 手算金标准（最小场景人脑可验算）+ 属性测试 + 对抗用例 |

### 8.3 三条铁律

1. **差异必须逐条归因**：我错 / 他错 / 口径不同 / 环境差异——
   **不允许“大致对上就算过”**（“大致对上”是把未知重新包装成已知）。
2. **验收标准升级**：从「测试全绿」升为「测试全绿 **+ 与独立实现差异已归因**」。
3. **第一版的目标是暴露，不是通过**：全区间扫描 / 真实数据 / 差分这三件是**暴露装置**（找错），
   不是验证装置（证明对）。把“第一版就正确”当验收标准，会逼出“改测试让它变绿”。

### 8.4 实例

| 实例 | 结果 |
|---|---|
| 全区间涨跌停比对（自研 vs rqalpha bundle，逐日 8486 天） | **1464 天差异**，顶出“创业板 ETF 自 2020-08-24 起 ±20%”这条写错的规则；**不做差分就会一路绿灯** |
| 边界差分（二进制浮点 vs 十进制取整） | 8 天 ±1 tick 差异，定位到 `3.155×0.9` 的浮点边界 |
| 手算金标准（最小场景人脑可验算） | 份额折算 / 分红事件逐项核对 |

## 九、一页流程

```text
引入任何依赖 / 借鉴任何方案前
        │
        ├─ 1. 拉历史：git clone --filter=blob:none --no-checkout
        │
        ├─ 2. 找高频坑区：fix 密度 + 关键词 + Revert + 改动最频繁的文件
        │
        ├─ 3. 优先读 tests/（含 issue 号的最好）；金标准快照次之
        │
        ├─ 4. 每条坑位写成四元组（坑 / 证据 / 影响 / 动作）
        │
        ├─ 5. 按 A/B/C/D 分级落库：A 类立刻改规格补测试
        │
        ├─ 6. 写调研文档时：每条引用拆信息单元 + 标去向（采纳/拒绝/暂缓）
        │     对照表必须有「原文要点」列；禁止只有「做法 → 启示」两列
        │
        ├─ 7. 冻结前回扫一次：把引用重过一遍，找“无去向标签”的孤儿信息
        │
        ├─ 8. 先跑通大佬的输出，再写自己的；第一版追“差异清单”而非“对”
        │     差异逐条归因（我错/他错/口径不同），不允许“大致对上就算过”
        │
        └─ 9. 无补丁史时改走“扫边界”：全区间/全参数差分比对
```

> **1~5 防“没读到”，6~7 防“读到了但提取时丢了”，8 防“未知的未知”。**
> 三者对应三类缺陷，缺任何一层都会在对应类型上反复踩坑。

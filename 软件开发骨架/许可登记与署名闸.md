# 骨架：许可登记与署名闸（LICENSE 闸）

> 适用于：任何**要分发**或**对外提供服务**的软件项目（尤其引入开源依赖后）。
> 核心问题不是"要不要署名"，而是——**你怎么证明每个依赖的许可都被核过、且署名没有漏**。
> 答案：**单一真源 + 机械判据 + 四道闸 + 实测红过**。

---

## 1. 单一真源：`licenses/manifest.json`

**一份 JSON 是所有许可结论的唯一来源**，产品内「关于」页、公开文档、发行包里的许可目录三处都**由它生成，不手写**。

每条组件记录的字段（只增不减）：

| 字段 | 说明 |
|---|---|
| `id` / `name` / `version` | 与锁文件对齐的键 |
| `layer.code.spdx` | ① 代码许可（标准 SPDX 表达式） |
| `layer.code.evidence` | 许可原文锚点（`file:...` 相对路径）＋ 读取日期 —— **不许凭印象** |
| `layer.weights` | ② 模型权重许可（不适用写 `null`，但**必须显式表态**） |
| `layer.additional_terms` | ③ 附加条款（署名要求 / 终止条件 / 随附文本义务） |
| `attribution.required` ＋ `attribution.template` | 是否须在产品内显著署名；模板写死 `{component, usage, url}`，**不由人撰写** |
| `serves_online` | 是否进对外服务链路（离线内部使用不触发署名义务） |
| `distribution` | 随包分发的形态（`npm` / `pip` / `fonts` / `binary`…） |
| `introduced_at` / `reviewed_at` / `owner` | 引入 / 复核日期与责任人（巡检输入） |

## 2. 四道闸（时机表）

| 闸 | 时机 | 跑什么 | 阻断 |
|---|---|---|---|
| 1 · 本地 | 开发时可选 | 快速模式：清单一致 + 字段完整 | 否（提示） |
| 2 · CI（PR） | 每次提交 | 清单**双向对账** + 三层字段完整 + 判据 b/c + **许可正文独立裁判** | ✅ 阻断合并 |
| 3 · 构建期 | 每次构建 | 产物中找不到强制署名文案 → 构建失败 | ✅ 阻断构建 |
| 4 · 发布前 | 发布清单 | 关于页可达（人工确认）+ 发行包许可目录完整 + 与锁文件终检 | ✅ 阻断发布 |

## 3. 生成器给草稿，结论归人（三条硬规矩）

1. **元数据不是结论**：包元数据里的 `License` 字段经常是自由文本或过时声明。
   脚本只在值是**合法 SPDX** 时才采用；否则写占位符 `<待人工确认>`，让检查失败，
   逼着人打开 `evidence.anchor` 指向的许可原文核实后再填标准值。
2. **人工值不被覆盖**：脚本每次刷新只更新版本与证据锚点，`spdx`（人工核实过的）、
   `additional_terms`、`attribution.*` 一律保留 —— 否则"跑一次生成器就把人的结论冲掉了"。
3. **`required = true` 必须三处齐**：模板三字段非空（判据 b）＋ 公开文档同句文案（判据 c）
   ＋ 构建产物同句文案（判据 d）；三处文案由**同一个函数**拼出，防止文案漂移。

## 4. 独立裁判：声明 ↔ 上游 LICENSE 正文

`spdx` 来自元数据**声明**，LICENSE 文件正文是**独立第二条路径**。两者不一致 = 差异，必须逐条归因。

**两个真实实例（都发生在本骨架的第一次落地）**：

| 实例 | 现象 | 归因 | 处置 |
|---|---|---|---|
| `pytest-django` | 元数据写自由文本 "released under the BSD (3-clause) license" | **元数据不合规**（不是错） | 打开 LICENSE 正文核实 → 人工填 `BSD-3-Clause` |
| BSD-3 变体措辞 | 检查脚本把某 BSD-3 判成 BSD-2 | **我方检测器太窄（我方错）** | 识别规则补第二种合法措辞（`endorse or promote` + `specific prior written permission`） |

> 教训：**"检查器通过了"不等于"没问题"**——第一次跑独立裁判时，要先假定检测器本身也会错。
> 读不到正文的条目要显式打印 `[!] 无独立裁判，需人工核对`，**不许静默跳过**。

## 5. 红过纪律：防线必须真的红过一次

三种注入用例（脚本自带，见 `tools/许可闸/test_injections.py`）：

| # | 注入 | 期望 |
|---|---|---|
| 1 | 声明 `required = true` 但不渲染署名 | 构建期断言 **失败** |
| 2 | 新增依赖但不登记 manifest | CI **红**（清单不一致） |
| 3 | 删掉公开文档里的同句署名 | CI **红**（判据 c） |

再加一条**对照组**：基线全一致时必须通过 —— 防止写出一条"永远红"的假防线。

## 6. 不引入扫描工具（P1 级项目的取舍）

`pip-licenses` / `license-checker` / `syft` 类工具**扫的是声明字段**，
扫不到权重层与附加条款，而且引入即新增依赖。自持最小脚本（仅标准库）足够。

**换用成熟工具的触发条件**：依赖数超预算 / 出现一次漏登记事故 / 需要对外交付 SBOM。

## 7. 落地清单

```
licenses/README.md            # 说清"唯一真源 + 改法"，禁止手改生成物
licenses/manifest.json        # 唯一真源（生成 + 人工复核）
THIRD-PARTY-NOTICES.md        # 生成物：公开文档落点
tools/许可闸/license_manifest.py     # 六模式脚本（generate/check/notices/check-build/verify-text/budget）
tools/许可闸/test_injections.py      # 11 条注入 + 对照组
```

- `--budget` 顺带做**依赖预算**统计（把直接依赖按前端 / 后端 / 工具分桶对照上限）；
- **移除 / 修改署名块 = 高风险变更**：必须改 manifest + 写明理由 + 证据账本留痕；
  产品界面**不得**提供"隐藏署名"开关；
- 传递依赖不在 manifest（只登记直接依赖）→ 传递依赖义务由直接依赖的上游承担；
  需要 SBOM 时另评。

# 骨架：项目协作规范

> 适用于：多人或人机（AI）协作的代码项目。
> 
> 核心目标：**让协作者（包括未来的自己）能看懂、能复现、能回退。**

---

## 1. 改动透明原则

每次完成文件改动后：
- 尝试 `git status` → `git add` → `git commit`
- **必须明确告知**：
  - commit 是否成功
  - push 是否成功（如失败，说明原因）
  - 改了哪些文件、哪些模块
  - 实现了什么功能 / 修复了什么问题
  - 是否影响前端/后端/数据库/部署/文档

---

## 2. 先理解再修改

- 不查看相关文件就不大改
- 优先沿用已有结构、命名、风格、业务约定
- 保持改动小而清晰，只改与当前任务直接相关的内容

---

## 3. 失败不隐瞒

- 命令、测试、构建、提交、推送失败 → 直接说明失败点和错误信息
- 提供下一步处理方式

---

## 4. 技术选型原则

- 优先调研和评估成熟、持续维护、许可证兼容的开源方案
- 能通过移植、适配或组合满足需求时，不重复从零实现
- 自研时必须记录：评估过的候选、拒绝原因、取舍依据

---

## 5. 语言与注释规范

| 场景 | 规则 |
|-----|------|
| 面向用户的说明 | 中文 |
| `.md` 文档 | 中文为主 |
| 代码变量名、函数名 | 英文 |
| 代码注释 | 优先英文，关键逻辑加中文解释 |
| 产品界面文案 | 遵循项目已有 i18n |

---

## 6. 命令展示规范

向用户提供需在项目中执行的命令时：
- 代码块第一行必须先进入对应项目目录
- 示例：
  ```bash
  cd "D:\project\my-project"
  npm test
  ```

---

## 7. 测试与验证

- 代码改动后根据影响范围运行合适检查
- 没运行测试时，必须说明原因

---

## 8. 安全与隐私

- 不提交真实密钥、Token、密码、Cookie
- `.env`、密钥文件只使用占位符和配置说明

---

## 9. 部署规则

- `git push` 成功且影响线上功能 → 按项目部署流程更新
- 仅文档/规则/注释改动 → 说明无需部署

---

## 10. 最终汇报模板

```
## 本次改动

### 文件列表
- file1.py（模块A：修复了xxx）
- file2.md（文档：更新了xxx）

### 功能/修复/调整
- xxx

### 检查结果
- [ ] 测试通过 / 失败原因：xxx
- [ ] 构建通过 / 失败原因：xxx

### Git 状态
- commit: [hash] "msg"
- push: 成功 / 失败（原因）

### 待用户操作
- [ ] xxx
```
